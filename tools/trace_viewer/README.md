# Trace Explorer

Откройте `index.html` в браузере и выберите `trace.json` либо перетащите файл в окно. Страница автономная: сервер, установка зависимостей и интернет не нужны. Загруженный лог остаётся в браузере. Страница не выполняет код из лога.

Вверху показана последовательность посещений нод, включая повторы. Выберите посещение, чтобы увидеть его входное состояние и события. «Весь маршрут» показывает исходный запрос, начальное состояние, все события и фактический `final_state` из файла.

Слева доступны поиск, фильтры типов событий, режим «Только ошибки», выбор отдельных полей по пути и просмотр JSON. `*` в пути означает любой элемент массива. «Основные» скрывает технические метаданные, «Все» возвращает все поля. Сворачивание объекта или длинного текста сохраняет его доступным для раскрытия. Поиск работает по полному содержимому события, даже если часть полей скрыта. Фильтры событий не скрывают справочные блоки начального/итогового состояния. Экспорт сохраняет события выбранного посещения (или всего маршрута) с учётом фильтров и выбранных полей; это сокращённая выгрузка для анализа.

`input_state` в настройках и экспорте — добавленная просмотрщиком группа восстановленного входа ноды; в исходном файле такого поля нет. Заголовки карточек и навигация остаются видны при скрытии полей, чтобы сохранять ориентацию в маршруте.

## Что хранится в trace.json

Описание сверено с `run_trace.py`, `main.py`, `pipeline.py`, `code_nodes.py` и эталонным логом `results/2026-10-16/Эталонный запрос/1/trace.json`.

| Группа | Содержание и назначение |
| --- | --- |
| Верхний уровень | `prompt_name` — имя эксперимента; `prompt` — исходный запрос; `started_at`, `finished_at` — границы запуска; `status` — завершился ли запуск без необработанного исключения; `error` — необработанная ошибка запуска или `null`. |
| `events` | Хронологический журнал. У события есть `sequence` (порядковый номер), `time` (время с часовым поясом) и `type` (вид события). События показаны в порядке массива, без сортировки по времени. |
| `initial_state.state` | Состояние графа перед обработкой. В примере содержит исходное сообщение, флаг ошибки, пустой результат генерации и пустые истории агентов. |
| `model_input` | Фактический вызов LLM: `node`, идентификатор модели `model`, пакеты `messages`. `run_id` связывает запрос с ответом или ошибкой; `parent_run_id` указывает родительский запуск callback. |
| `model_output.response` | Результат вызова модели. `generations` — вложенные массивы вариантов генерации; каждый вариант содержит `text` и `message`. В этом логе это часто две формы одного ответа, а не два вызова. |
| `model_error` | Ошибка обращения к модели, связанная с `model_input` по `run_id`. В эталонном запуске таких событий нет; просмотрщик поддерживает их. |
| `node_update` | `node` — завершившаяся нода; `update` — возвращённые ею изменения состояния, а не полное состояние и не обязательно точная копия ответа LLM. |
| `code_check` | `stage` — этап проверки; `returncode` — код завершения процесса; `stdout` — обычный вывод; `stderr` — диагностический вывод. `error` появляется при исключении, например таймауте, когда кода возврата может не быть. |
| `final_state` | Накопленное состояние после прохождения графа. Его основные поля описаны ниже. |

### Message и содержимое ответа

`messages`, `agent_code_history`, `agent_error_history` и `response.generations[*][*].message` содержат сообщения LangChain. `model_input.messages` имеет дополнительный уровень массива: это пакеты сообщений, переданных модели.

- `type`: роль сообщения — `system` (инструкция), `human` (запрос или коррекция), `ai` (ответ модели), а в других логах может быть `tool`.
- `content`: собственно текст запроса, инструкции, диагностики или ответа. Иногда это строка с JSON (`prefix`, `imports`, `code`), а не готовый объект. В других форматах LangChain здесь могут быть блоки содержимого.
- `tool_calls`: структурированные вызовы инструментов и их аргументы, когда они присутствуют. Само наличие `tool_calls` не доказывает, что инструмент был выполнен: нужны события выполнения/результата.
- `additional_kwargs`: дополнительные данные адаптера. В данном логе при структурированной генерации встречается `parsed` — разобранный объект кода; `content` одновременно содержит JSON-строку. По умолчанию эта группа скрыта, поскольку результат доступен в `node_update.update.generation`; при необходимости её можно включить.

Технические метаданные провайдера, идентификаторы сообщений и статистика токенов по умолчанию скрыты. Для понимания маршрута и причин повторной генерации они обычно не нужны.

### Основные поля State / Final State

| Поле | Назначение |
| --- | --- |
| `messages` | Общая накопленная история: исходный запрос, уточнение классификатора, диагностики ошибок и финальный анализ. Это не обязательно все промпты всех агентов. |
| `input_classifier_response` | Уточнённая постановка задачи, которую использует генератор кода. |
| `generation` | Текущая версия решения: `prefix` — объяснение подхода, `imports` — импорты, `code` — основной Python-код. В начальном состоянии может быть пустой строкой. |
| `agent_code_history` | История генератора кода: системная инструкция, начальная задача, решения и запросы на исправление. |
| `agent_error_history` | История диагностики: запросы с кодом и ошибкой, ответы диагностического агента. |
| `error` | Флаг управления графом: `"yes"` направляет на повторную генерацию, `"no"` позволяет перейти к итоговому анализу. Отличается от верхнеуровневого `error` с исключением запуска. |
| `sim_logs` | Вывод последней успешно завершившейся проверки кода: `stdout + stderr`. Пустая строка означает отсутствие вывода. |

Правила накопления определены в `GraphState`: три списка (`messages`, `agent_code_history`, `agent_error_history`) дополняются через `operator.add`, остальные поля заменяются. Просмотрщик использует именно эти правила для восстановления входа каждой ноды. Для другого графа с иными reducers такая реконструкция может быть неверной; фактические `model_input`, `node_update` и `final_state` остаются доступны отдельно.

## Что можно и нельзя восстановить

`model_output` не содержит `node`, но его принадлежность точно восстанавливается по `run_id` соответствующего `model_input`. `code_check` не содержит ни ноды, ни `run_id`; в текущем последовательном графе его можно отнести к посещению, завершённому следующим `node_update`. Интерфейс прямо помечает это как вывод по порядку событий.

`node_update` отмечает завершение ноды. Самостоятельных событий начала ноды, выборов условных рёбер и отдельных вызовов `decide_to_finish` здесь нет. Поэтому маршрут — реконструкция фактически посещённых нод, а не полная топология LangGraph. Время события не даёт точного времени работы всей ноды. События после последнего `node_update` показываются как незавершённый участок.

Для параллельных веток, вложенных графов и точного измерения времени потребуется расширить логирование: добавить `node_start`, `node_end`, идентификатор посещения, принадлежность каждого `code_check` и события переходов. Эти изменения в систему логирования в данной задаче не вносились.

## Проверка просмотрщика

Из корня проекта: `node tools/trace_viewer/test.cjs`. Проверяются реальные события эталона, связь вызовов с нодами, накопление состояния, фильтрация вложенных полей и обработка неполного лога. Тесты не обращаются к LLM и не запускают код из trace.
