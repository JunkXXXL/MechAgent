# Логика построения физической модели

`pipeline.py` собирает граф LangGraph, `code_nodes.py` реализует его узлы.
Роли и инструкции агентов находятся в `agents.yaml`, задания — в `tasks.yaml`.
Пути к этим двум YAML-файлам определяются относительно модуля, а не текущего каталога.

Пайплайн выполняется последовательно:

1. `input_classifier` получает исходный запрос и формирует `SimulationSpecification`.
   Для каждого параметра указаны имя, символ, смысл, значение, единица СИ, исходное
   значение с единицей, категория, значимость и источник (`user` или `inferred`).
   Число параметров зависит от задачи. Допущения, переменные состояния, метод расчёта
   и требуемые результаты описываются отдельно. Спецификация сохраняется в JSON.
2. `subsystem_design` получает исходный запрос и спецификацию. Агент выделяет
   физические подсистемы, описывает уравнения, состояния, сигнатуры функций и связи:
   кто кому передаёт величину, её имя, единицу измерения, знак и систему координат.
   Документ также задаёт порядок вычислений и решение связанных ограничений.
   `physical_subsystems.md` записывается **до генерации кода**.
3. `code_generation` по этому документу реализует функции всех подсистем.
   Результат сохраняется в `subsystems.py`; запуск симуляции в этом модуле не предусмотрен.
4. `model_assembly` получает функции, описание взаимодействий, спецификацию и
   исходный запрос. Он пишет код связей, численного решения, CLI и вывода результатов.
   Код функций сохраняется в итоговом `model.py` вместе с кодом сборки:
   итоговая программа не требует отдельного импорта `subsystems.py`.
5. `code_execution_import_check` проверяет импорты и исполнение в отдельном Python-процессе,
   во временном каталоге, с тайм-аутом 300 секунд. При ошибке диагностирующий агент
   получает полный код и логи; диагноз передаётся обоим агентам реализации.
   Повторяются этапы 3–5, максимум три попытки по умолчанию (`max_iterations`).
   После исчерпания попыток запуск завершается с ошибкой, без итогового объяснения.
6. `create_insight`, если включён, кратко описывает **полученную физическую модель**,
   её параметры, ограничения и запуск Python-кода. Отчёт сохраняется в `simulation_report.md`.

```text
START -> спецификация -> подсистемы (MD) -> функции -> сборка -> проверка
                                            ^                   |
                                            |--- диагноз -------| ошибка
                                                                |
                                                   успех -------+
                                                     |
                                         отчёт (если включён) -> END
```

## Запуск

Из каталога проекта, в окружении с установленными зависимостями и настроенным
`OPENAI_API_KEY` (например, через `.env`):

```powershell
python main.py request.yaml
python main.py request.yaml --skip-insight
python main.py request_suspension.yaml --skip-insight --output-dir results
```

`--skip-insight` пропускает вызов последнего агента. Сборка и проверка модели сохраняются.
В папке каждого эксперимента `results/<дата>/<имя запроса>/<номер>/` создаются:

- `specification.json` — параметры, единицы и допущения;
- `physical_subsystems.md` — физические подсистемы и обмен величинами;
- `subsystems.py` — функции подсистем;
- `model.py` — самостоятельная запускаемая модель;
- `simulation_report.md` — объяснение модели, если последний агент включён;
- прежние `<имя запроса>.py`, `<имя запроса>.md` и `trace.json`.

Промежуточные документы сохраняются сразу после соответствующего этапа и остаются
доступны при ошибке следующих этапов. При повторной генерации Python-файлы обновляются.
`model.py` записывается до проверки, поэтому при неуспешном запуске он может содержать
последний неработающий вариант. Статус проверки следует смотреть в отчёте и trace.
Проверочные CSV и рисунки создаются во временном каталоге и удаляются после проверки;
для получения этих результатов запустите сохранённый `model.py` самостоятельно:

```powershell
python model.py --help
python model.py
```

При прямом вызове из Python можно отключить последний этап на уровне графа:

```python
from pipeline import build_pipeline

agent = build_pipeline(enable_insight=False)
result = agent.invoke({
    "user_request": "Смоделируй колебания груза на пружине",
    "artifact_dir": "output/spring_model",
})
```

Либо передать `"enable_insight": False` в состояние стандартного `agent`.
Если `artifact_dir` не задан, документы сохраняются в уникальный `output/<id>/`
относительно каталога проекта. При прямом запуске `main.py` не участвует, поэтому
создаются только файлы этапов, без общего отчёта эксперимента и `trace.json`.

## Проверка изменений

```powershell
python -m unittest discover -s tests -v
```

Тесты выполняют настоящий граф и запускают детерминированную тестовую модель в
дочернем Python-процессе. Ответы LLM заменены тестовыми: внешние API не вызываются.
Проверяются сохранение файлов, передача контекста, оба способа отключения отчёта,
исправление ошибки и остановка после исчерпания попыток. Исполнение Python само
по себе не доказывает физическую корректность сгенерированной модели.
